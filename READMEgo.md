# READMEgo — как выкатывать новые версии, не ломая работающее

> Принцип: **миграции БД идут ПЕРЕД кодом**, код откатываемый, база — нет. Каждая версия обратимо
> применима в пределах одного релиза. Фича-флаг `VITE_API_MODE` позволяет держать два бэкенда
> (supabase/own) параллельно до полного переезда.

## 1. Правило версий

- Каждая правка = +1 к версии (см. MIGRATION.md, заголовки `## vX.Y.Z`).
- Патч (1.33.x): правки без изменения схемы БД.
- Минор (1.34.0): новая фича; если трогает схему — обязательна миграция `migrations/NNNN_*.sql`.
- Метки `// vX.Y.Z:` в коде на каждом изменённом блоке.

## 2. Выкатка новой версии (пошагово)

### ШАГ 1. Локальная проверка (до пуша)

```powershell
npm run typecheck          # фронт: 0 ошибок
cd api && npm run typecheck && npm run build && cd ..   # API: 0 ошибок
```

### ШАГ 2. База данных — СНАЧАЛА

```powershell
# Новая миграция добавлена? (migrations/NNNN_description.sql)
# Порядок строгий: 0001 (только чистые базы) → 0002 → 0003 → … по возрастанию.
# Прод: применить через psql/DBeaver под app_admin:
#   psql "postgres://app_admin:…@host:5432/erp" -f migrations/0006_xxx.sql
# Проверка: pgTAP зелёный
pg_prove -U postgres tests/rls_isolation.sql
```
**Железное правило:** код, требующий новую миграцию, НЕ деплоится, пока миграция не применена на
проде. Иначе приложение упадёт на отсутствующей колонке/таблице.

### ШАГ 3. Пуш в GitHub → Coolify деплоит автоматически

```powershell
git add -A
git commit -m "vX.Y.Z — описание"
git push origin main
```
Coolify: API пересобирается из `api/Dockerfile`, фронт из корня. Healthcheck `/healthz` —
если приложение не поднялось, Coolify не переключает трафик (zero-downtime при зелёном healthcheck).

### ШАГ 4. Переключение фронта между бэкендами (без пересборки кода)

```powershell
# В Coolify → Environment фронта:
VITE_API_MODE=own        # или supabase — фронт пересобирается, логика переключается флагом
VITE_API_URL=            # пусто = same-origin (прокси /api → сервис API)
```

### ШАГ 5. Smoke-тесты после каждой выкатки (2 минуты)

1. Вход в CRM → дашборд загрузился.
2. Создать тестового поставщика → в списке виден.
3. Открыть ЛК по токену `/s/<token>` → данные + брендинг.
4. Отправить публичную форму (embed или /forms/supplier) → запись появилась, письмо ушло.
5. Настройки → Домены открываются (own-режим).

### ШАГ 6. Откат, если сломалось

- **Код**: Coolify → Deployments → откат на предыдущий коммит (фронт+API).
- **База**: миграции аддитивны — старый код с новой схемой работает; destructive-изменения
  (переименование/удаление колонок) в проекте запрещены без отдельного решения.
- **Флаг**: `VITE_API_MODE=supabase` возвращает прежний бэкенд одной переменной.

## 3. Обновление без полной выкатки (горячие правки)

| Ситуация | Что делать |
|---|---|
| Только тексты/вёрстка фронта | пуш → пересборка фронта (API не трогается) |
| Только логика API | пуш → пересборка API (фронт не трогается) |
| Только настройки (не код) | правка `app_settings` в интерфейсе Настроек — без деплоя |
| Почта/SMTP | env API в Coolify → перезапуск сервиса |

## 4. Цикл версий (как не накапливать долг)

- Перед стартом новой фичи — `npm run typecheck` зелёный.
- В конце — запись в `MIGRATION.md` (симптомы/причины/проверка), бамп версии в 3 местах:
  `package.json`, `api/package.json`, `src/constants/index.ts` (APP_VERSION), строка в README.md.
- Раз в квартал: прогон восстановления из бэкапа (см. README.md «Бэкапы»).

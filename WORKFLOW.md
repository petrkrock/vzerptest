# VZCRM — Регламент разработки и выкладки фич

Версия документа: 1.1 (v1.30.x) — добавлен раздел «Стиль кода»
Назначение: единый порядок работы от задачи до продакшена. Все правки идут по нему.

---

## 0. Принципы (без них ничего не начинаем)

1. **Ничего не ломаем.** Существующая логика, синк, права, RLS — не трогаем без отдельной задачи.
2. **Ничего не выдумываем.** Делаем ровно по списку правок. Вопросы — к постановщику, а не самодеятельность.
3. **Каждая правка — версия.** Нумерация `1.30.x`, следующая правка = следующий номер.
4. **Никакого «глазами».** Каждая версия перед отдачей прогоняется компилятором (esbuild/tsc). «Не компилируется» не должно доходить до тестировщика.

## 1. Пайплайн: от задачи до продакшена

### Шаг 1. Постановка
- Задача формулируется списком (как «косяки»/«шаги»).
- Перед стартом: прочитать затрагиваемые места (навигация, права, синк, edge function).
- Зафиксировать план: какие файлы, какие данные, нужны ли миграции/деплой функций.

### Шаг 2. Разработка (локально)
- Работаем в `.env` с **боевыми** ключами Supabase (демо-режим выключен).
- `npm run dev` → правки → проверка в браузере.
- Если задача касается edge function — проверяем контракт: тело запроса ↔ ответ, токен/PIN, понятные ошибки.

### Шаг 3. Миграции данных (если нужны)
- Код миграции → `src/lib/store.ts` (блок миграций настроек) — **всегда вне узких гейтов**, иначе существующие базы не получат изменения.
- Схема → `supabase/schema.sql` (для новых установок).
- **Отдельный SQL для боевой базы** собираем в конце задачи (`ALTER TABLE ... IF NOT EXISTS ...`). Код не должен требовать колонку раньше, чем она создана: либо пишем колонку только при непустом значении, либо SQL выполняется ДО выкладки фронта.

### Шаг 4. Валидация (обязательно перед упаковкой)
```
# каждый изменённый .ts/.tsx:
esbuild <файл> --loader:.tsx=tsx --outfile=/dev/null
# или полная сборка:
npm run build
```
- Баланс тегов, нет мёртвого кода, неиспользуемых импортов, undefined-идентификаторов.
- Поиск по проекту на «остатки»: старые названия, удалённые поля, дубли.

### Шаг 5. Контрольная точка (версионный архив)
- Собираем `vzcrm_vX.Y.Z.zip` из чистого дерева (без node_modules, без .env).
- Архив = точка отката. Имя — строго по версии.
- К релизу список: что изменено, какие файлы трогать, какие SQL выполнить, какие функции задеплоить.

### Шаг 6. Проверка (локально против боевых данных)
- Заменить файлы из архива → `rm -rf node_modules/.vite` → `npm run dev` → Ctrl+F5.
- Пройти **сценарий задачи** end-to-end (по шагам постановки).
- Проверить смежное: не сломались ли синк, ЛК, настройки.

### Шаг 7. Выкладка на продакшн (порядок строгий)
1. **SQL** на боевую базу (ALTER, политики, бакеты).
2. **Деплой edge functions**: `supabase functions deploy <name> --no-verify-jwt`.
3. **Сборка фронта**: `npm ci && npm run build` → выкладка статики.
4. **monitor-server** (если менялся): перезапуск pm2/systemd.

### Шаг 8. Проверка на проде
- Чек-лист из 3–5 пунктов по задаче (открыть раздел, сохранить, F5, ЛК/CRM).
- Журнал синка CRM + логи edge function — нет ли ошибок.

### Шаг 9. Откат (если что-то пошло не так)
- Фронт: предыдущий zip.
- Edge function: деплой предыдущей версии из архива релизов.
- База: откат миграций только через бэкап (Supabase → Backups). `ALTER ... IF NOT EXISTS` откату не мешают.

## 2. Правила для типов задач

| Тип задачи | Обязательные пункты |
|---|---|
| Новые поля сущности | типы → маппер (ОБЕ стороны!) → схема → SQL ALTER → проверить snake_case/camelCase |
| Настройки (settings) | миграция default **вне гейта** → VOLATILE_SYNC_KEYS не трогаем без причины |
| Edge function | CORS (apikey!), токен из query/тела, понятные 4xx, анти-брутфорс PIN |
| ЛК поставщика | модалки/блоки на **верхнем уровне** (не внутри одной вкладки!) |
| Удаление данных | маппер пишет `null`, иначе удаление «восстанавливается» из базы |

## 3. Стиль кода

1. **Версионная метка.** Каждая нетривиальная правка помечается в коде:
   `// v1.30.34: <что делает блок>`. По меткам потом ищутся изменения.
2. **Мапперы — обе стороны.** Новое поле сущности: тип в `src/types/index.ts` →
   чтение и запись в мапперах `src/lib/supabase.ts` → `ALTER TABLE ... IF NOT EXISTS`.
   Удаление поля — маппер пишет `null`.
3. **Мёртвый код убираем сразу** (неиспользуемые функции, импорты, состояния).
   Проверка: поиск по проекту имени перед удалением.
4. **UI — только примитивы проекта** (`docs/DESIGN.md`): классы из `index.css`,
   палитра бренда, sonner, lucide-react. Без новых библиотек и цветов.
5. **Форматы:** даты в БД ISO `YYYY-MM-DD`, показ `дд.мм.гггг`; деньги `tabular-nums` + `₽`.
6. **Язык интерфейса — русский**, тексты в коде — русские, комментарии — русские,
   идентификаторы — английские (camelCase).
7. **Никаких нативных alert/confirm/prompt** — кастомные модалки и toast.
